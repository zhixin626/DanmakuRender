# 第9项：双线性缩放与持有缓冲

状态：完成。实际约30分钟，预估45–75分钟。代码仅在隔离worktree，未修改正式目录，未暂存用户配置/BAT修改。

1. **改了什么**：`gpu_render.NV12Buffer`用单个CuPy kernel双线性缩放Y/UV并补黑边，坐标/权重按源尺寸、画布尺寸、色度位置缓存。`decode_frames`复用3个持有缓冲，按拷贝完成事件保护SDK表面；原型`main()`原样迁到`perf/run_gpu_render.py`。
2. **为什么这样改**：最近邻缩小时锯齿明显，且原实现每帧生成索引及持有对象。三槽对应调度器的当前帧、预读帧和下一次解码，避免提前覆盖仍被引用的数据；量化边界采用像素中心坐标。
3. **问题与解决**：本轮仍保留解码表面→持有缓冲的一次D2D拷贝，再拷贝/缩放进FrameRing；不再每帧创建持有对象，也不再整条默认流同步。每次SDK推进前只等待尚未完成的源拷贝事件，消费端等待ready事件，关闭生成器时也完成最后一次拷贝。
4. **意见和想法**：600帧持有缓冲构造次数从600降为3，但解码加持有的摊销耗时基本持平，不能声称该部分已提速。画布路径从0.628降至0.089ms/帧（约7.08倍），实际长片CPU核·秒和风扇噪声本轮未重新测量。
5. **整体看法**：95项单测、12组原生采样测试、24,115个输出时间点的源帧签名/PTS比较及完整媒体自检均通过；两段G全部逐帧扫描，0候选/0闪烁。三倍发丝/衣物文字截图中未见G比E明显更多的锯齿，普通1080p增强素材成片与第8项逐字节一致。
6. **给Claude的建议**：请重点审查三槽在预读和多帧批次中的生命周期、ready事件跨流等待、UV相位和pitch。新追加的“今晚任务”已拉取，但按用户本条明确要求，本轮完成7/8/9即停下；停止恢复、字体回退、单词换行及两小时复测不计为本轮完成。

## 拷贝与色度的具体取舍

- `Decode()`提供的未锁定表面可能在后续调用中复用；CFR需要先取得后继帧PTS才能决定当前帧的重复区间。直接把该表面交给异步编码器无法证明其持有期，因此本轮保留源持有拷贝。
- 已核对本机绑定：`GetLockedFrame()`存在并返回整数裸指针，`UnlockFrame()`存在。采用锁帧理论上能去掉持有拷贝，但需要另外处理批次、PTS配对、pitch和取消解锁；本轮不引入这条生命周期更复杂的路径。[NVIDIA锁帧接口说明](https://docs.nvidia.com/video-technologies/pynvvideocodec/pynvc-api-reference/decoder.html)
- 真实源元数据为`chroma_location=left`；UV横向使用四分之一采样相位，纵向为二分之一。另测center/top/topleft/bottom/bottomleft到输出left的相位映射，U/V分别采样，kernel按实际行/列stride访问。
- 缓存保留在每个FrameRing槽位；相同源→画布→色度位置不重建坐标。帧尺寸切换时各持有槽按需重建，仍只保留三个当前槽。
- 0.5/0.25/0.75是像素/色度的几何位置，3是调度器预读所需槽数，256是CUDA线程块尺寸；均非用户画质或码率默认值。帧率、画布、编码器和码率继续来自源/配置。
